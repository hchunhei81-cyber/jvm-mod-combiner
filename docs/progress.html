    LATEST UPDATE · 2026-11-10

    Hostile-mob mirror pipeline added in the working tree

    The current Java sources add NeoForge handling for Fabric monster spawn/update messages, entity mirrors, and an ACK/retry path. The Rust DataBus continues to restrict protected state messages to the registered Fabric name.

    Main-branch context: The checked main history includes loader detection/DataBus registration (f2171ad), Minecraft 1.21.4 Agent/classpath work (f146f27), and the documentation refresh (e212414). The Java mob-mirror additions described here are uncommitted working-tree edits, not changes recorded in main.
    Verification status: These Java additions are source-level implementation only. The packaged Agent must be rebuilt from the current sources, then tested in the live Fabric/NeoForge setup. Monster removal is not implemented; do not treat mob synchronization as complete.
    Verified foundation

    Capabilities already established

    Previously verified prototype milestones remain separate from the newest untested source work.

    • Rust/JNI launcher and Java Agent initialization
    • Fabric and NeoForge startup experiments, plus experimental Forge startup
    • Rust TCP DataBus registration and JSON routing
    • Fabric-to-NeoForge player-state and RemotePlayer proof of concept
    In current source · runtime test pending

    Working-tree implementation

    These changes are present in the current bus_test source, but are not yet in the main-branch history.

    • NeoForge parses monster_spawn/monster_update, creates or updates mirrors, and clears mob mirrors when a world change is observed.
    • NeoForge sends monster_ack after applying a message; Fabric tracks pending sequence-numbered states and retries until acknowledged.
    • The existing Rust policy rejects non-Fabric player/monster state messages, but registration names are self-asserted and are not authenticated identities.
    Next steps

    Build, test, then complete lifecycle

    • Rebuild/package the Java Agent from current source and confirm the JAR contains the latest code.
    • Runtime-test normal player and mob delivery, unauthorized rejection, no forwarding, and connection continuity.
    • Test monster ACK/retry behavior, world changes, disconnects, and reconnect recovery.
    • Design and publish reliable monster_remove events; absence from the sampled render list is not proof of despawn.
    • Validate or otherwise constrain DataBus registration names.
    Scope: A source implementation or successful launcher startup is not end-to-end verification or general cross-loader mod compatibility.
