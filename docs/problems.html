ENGINEERING NOTES

Problems & solutions

A current, high-level view of what has been verified, what has a workaround, and what still needs implementation.

Prototype status: Fabric and NeoForge startup, DataBus routing, and one-way player mirroring have reached verified prototype milestones. They do not establish general mod compatibility or complete gameplay synchronization.
Verified foundation

Starting isolated loader environments

The Rust launcher has started Fabric 1.21.4 and NeoForge 1.21.1 in tested configurations. Forge 1.21.4 has reached experimental startup, but full gameplay stability is a separate target. The current Rust NeoForge launch configuration targets NeoForge 21.4.161 / Minecraft 1.21.4; verify that configuration separately from the previously documented 1.21.1 run.

Approach: Build loader-specific launch paths and resolve dependencies for each runtime instead of treating every loader as one interchangeable classpath.

Partly resolved

Dependency and classpath mismatches

Missing ASM/Mixin classes, game-provider discovery, LWJGL natives, and several tested launch-path issues have been addressed. A missing Netty class still requires verification against the exact runtime dependency graph.

Next: Complete manifest-based resolution, platform filtering, native handling, checksums, and conflict detection. Avoid broad library-directory scans.

Verified prototype

DataBus startup and basic routing

The Rust TCP DataBus registers named clients and routes JSON messages. Binding the listener synchronously before starting the accept thread resolved the observed startup race.

Limit: Basic routing does not yet enforce a fully versioned, validated protocol. The Rust source now rejects protected player and monster state types from non-Fabric registrations, but runtime tests remain open. Registration names are self-asserted and are not authenticated identities.

Source implemented · verify

One-way state policy and trusted identity

Fabric is the sole publisher for protected player/monster state types. Rust checks the connection's registered name and returns state_authority_violation without routing the rejected message or closing the connection.

Remaining: Runtime-test the behavior and constrain registration. The first message's registration name is client-supplied, so it is a routing label—not authenticated proof of which process connected. Rebuild/package the Java Agent from bus_test/.

Early source prototype

Hostile-mob synchronization

bus_test/MonsterSync.java samples visible, living hostile Fabric mobs by UUID on the game thread and emits monster_spawn and changed-state monster_update messages. Committed Java sources add a NeoForge receiver and ACK/retry path.

Incomplete: Missing-from-render iteration is not treated as removal; monster_remove is not published. The Java sources need to be rebuilt into the packaged Agent and runtime-tested with Minecraft.

Stability work remains

Mirror identity and recovery

RemotePlayer mirroring is a proof of concept. Initial timeout cleanup and mirror recreation have been observed, but stable identity, duplicate prevention, world changes, and reconnection recovery still need systematic testing.

Solution direction: Add stable UUID mapping, explicit lifecycle events, fresh-state recovery, and smoothing while keeping each game's tick loop independent.

Long-term design

Cross-loader behavior and compatibility

Matching coordinates does not make different versions, registries, mod APIs, or game logic equivalent. Arbitrary bytecode merging and native-code interception are not reliable universal solutions.

Solution direction: Define a normalized, versioned state protocol; use loader-specific adapters and explicit compatibility integrations; keep unsupported objects as visual proxies where appropriate.

Unresolved

Legacy Forge 1.16.5 startup

The native macOS installer path encountered a hash mismatch, and the older FML/ModLauncher launch pipeline was not brought to a working client state. Substituting newer launch components proved unreliable.

Current stance: Keep this as a separate, version-specific investigation; document it as unsupported if the maintenance cost outweighs the value.

Not a current target

Cross-process rendering and window composition

The current prototype registers JVMs and observes window metadata on macOS; position/size transactions exist in source, but live recovery remains unverified. Embedding and composition are not implemented. Combining GPU resources across independent clients is platform-specific and adds driver, synchronization, and lifetime risks.

Solution direction: Keep independent windows and prioritize reliable state synchronization. Consider platform-native composition only after core behavior is stable.

Unresolved · recovery unverified

Partial macOS window mutation and failed rollback

A real position/size operation partially changed a window, then failed verification. Rollback could not safely reacquire a matching Accessibility window, so recovery was not confirmed. CoreGraphics and Accessibility observations can differ during layout changes, and a title alone is not a reliable identity.

Fix direction: Revalidate window identity before every write, preserve specific API/read-back errors, and test partial-write and rollback failures without touching live windows. Do not treat source-level transaction support as verified recovery.
